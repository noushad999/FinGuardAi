# Data dictionary

All data is **synthetic** (generated by `simulator/`). No real customers, accounts or institutions.
Monetary values are in BDT. Timestamps are UTC; "local" means Asia/Dhaka (UTC+6, no DST).

## 1. Source extracts (`data/synthetic/*.parquet`, lake `raw/`, PostgreSQL `raw.*`)

### `customers`  — grain: one row per wallet account
| Column | Type | Description |
|---|---|---|
| customer_id | text, PK | `CUS_#######` |
| age | int | 18–80 |
| registration_date | timestamptz | Day the wallet was opened (≈18% open during the simulated window) |
| occupation_category | text | student, salaried_private, government_service, business_owner, farmer, day_laborer, garment_worker, homemaker, freelancer, transport_worker, retired |
| district / upazila | text | Home district (24 real district names, approximate centroids) / synthetic upazila code |
| customer_segment | text | Product tier: mass, mass_affluent, priority |
| kyc_level | text | full / basic |
| account_status | text | active / dormant at extraction time (**not used as a feature** – it leaks churn) |

### `devices` — grain: one row per handset observed
| Column | Description |
|---|---|
| device_id (PK) | `DEV_########` |
| customer_id | Most frequent account on the device |
| device_type / os | smartphone, feature_phone / Android, iOS, KaiOS, Proprietary |
| device_age_days | Handset age when first seen |
| first_seen / last_seen | Observation window |

### `merchants` — grain: one row per business counterparty
`merchant_id` prefix encodes the type: `MER_` retail merchant, `AGT_` cash-in/out agent, `BIL_` biller,
`TEL_` telecom operator, `BNK_` bank. Columns: merchant_type, merchant_category, district,
risk_category (low/medium/high), registration_date.

### `transactions` — grain: one row per transaction *attempt* (the Kafka event contract)
| Column | Description |
|---|---|
| transaction_id (PK) | `TXN###########` |
| event_time | When the customer initiated it |
| sender_id / receiver_id | For CASH_IN the sender is the agent; otherwise the sender is the customer and the receiver is a customer (P2P) or a business id |
| customer_id | The wallet whose balance the row describes (always a customer) |
| merchant_id | Business counterparty (null for P2P) |
| amount, fee, currency | Cash-out carries a 1.85% fee |
| transaction_type | P2P, MERCHANT_PAYMENT, CASH_IN, CASH_OUT, BILL_PAYMENT, MOBILE_RECHARGE, BANK_TRANSFER |
| channel | APP, USSD (feature phones), AGENT (agent-initiated cash-in; no customer device) |
| device_id, district, latitude, longitude | Where/how it was initiated |
| status, failure_reason | SUCCESS / FAILED with INSUFFICIENT_BALANCE, WRONG_PIN, NETWORK_TIMEOUT, LIMIT_EXCEEDED |
| balance_before / balance_after | Wallet ledger; `after = before − amount − fee` (debit), `+ amount` (credit), unchanged if failed |
| metadata | JSON: pin_attempts, network_type, app_version |

### `transaction_labels` — grain: one row per transaction (case-management feed)
| Column | Description |
|---|---|
| is_fraud / is_ato | Ground truth: part of a fraud case / an account-takeover case |
| fraud_scenario | One of 12 scenarios (see [fraud_detection.md](fraud_detection.md)) |
| fraud_case_id | Groups the transactions of one incident |
| fraud_reported_at | When the label became known (≈ lognormal delay, median 6 days after the case ended); null = never reported (5% of cases) |

Hidden ground truth used **only for evaluation**: `customer_ground_truth.parquet` (persona,
is_mule, mule_ring_id, night_shift, churn_date) and `merchant_ground_truth.parquet`.

## 3. ML outputs (`ml.*`)
transaction_scores (batch backfill of every transaction: fraud/ATO probability, anomaly
percentiles, split), customer_segments, churn_scores, graph_customer_metrics, graph_communities,
graph_suspicious_edges, customer_profiles. Written with full refresh by `data_engineering.pipelines load-ml`.

## 4. Star schema (`analytics.*`, dbt)

| Model | Type | Grain | Primary key | Foreign keys |
|---|---|---|---|---|
| dim_customer | dimension (SCD1) | customer | customer_id | location_key |
| dim_device | dimension | device | device_id | – |
| dim_merchant | dimension | business counterparty | merchant_id | location_key |
| dim_date | dimension | calendar day | date_key (YYYYMMDD) | – |
| dim_location | dimension | district | location_key (md5 of district) | – |
| fact_transactions | fact | transaction attempt | transaction_id | customer_id, device_id, merchant_id, date_key, location_key |
| fact_fraud_predictions | fact | (transaction, source, model_version) | prediction_key | transaction_id |
| fact_customer_activity | periodic snapshot fact | customer × local day | (customer_id, date_key) | customer_id, date_key |
| mart_transaction_risk | reporting | transaction (+ most authoritative prediction) | transaction_id | |
| mart_daily_kpis | reporting | local day | date | |
| mart_fraud_breakdown | reporting | (dimension, value) | | |
| mart_risk_score_distribution | reporting | 5-point score bucket | | |
| mart_top_suspicious_customers / merchants | reporting | customer / merchant | | |
| mart_segment_summary | reporting | segment | | |

**Natural vs surrogate keys.** Wallet, device and merchant ids are immutable ids issued by the
platform, so they are used directly as dimension keys (simpler joins for Power BI). Dates use
integer `date_key`; locations use a hashed key.

**Transformations.** Staging views type and rename columns, derive local date/hour, direction
(DEBIT/CREDIT), receiver customer for P2P, and keep *reported* fraud only (the business cannot
know unreported fraud). Core models join ML enrichments into `dim_customer`, compute
`accounts_seen` per device, and union batch and real-time predictions into
`fact_fraud_predictions` with the policy thresholds passed as dbt vars.

**Lineage.**
```
raw.transactions ─┬─ stg_transactions ─┬─ fact_transactions ─┬─ fact_customer_activity
raw.transaction_labels ─ stg_fraud_labels ─┘                  ├─ fact_fraud_predictions ─ mart_transaction_risk ─ marts
ml.transaction_scores ─┐                                      │
ops.risk_decisions ────┴─ stg_predictions ────────────────────┘
raw.customers ─ stg_customers ─ dim_customer ◄─ ml.customer_segments / churn_scores / graph / profiles
seeds/districts.csv ─ dim_location
```
`dbt docs generate` renders the full lineage graph.

**Tests.** 69 dbt tests: unique/not-null keys, relationships for every FK, accepted values, a
composite-key test for `fact_customer_activity`, and two singular tests
(`assert_balance_consistency`, `assert_no_transactions_before_registration`).

## 5. Feature catalogue
The 61 model features, grouped as transaction / behavioural / temporal / device / geographic /
network, are defined with descriptions in [`features/definitions.py`](../features/definitions.py).
All are computed from events strictly before the scored transaction.
