# Interview guide

Technical answers to the questions this project is designed to provoke. Numbers quoted come
from the committed reports in `reports/` (regenerated by `make pipeline`), not from memory.

---

### Why Kafka?
The transaction stream has several independent consumers with different speeds and failure
modes: a per-event risk engine, Spark for lake/aggregates, and later more (notifications, AML).
Kafka gives a **durable, replayable, partitioned log**: consumers track their own offsets, a slow
or crashed consumer does not block others, and history can be re-read after a bug fix. Keying by
`customer_id` guarantees per-customer ordering within a partition, which stateful features
(velocity, "time since previous transaction") require. Partitions are the unit of horizontal
scaling (6 partitions → up to 6 risk-engine workers). A plain queue (RabbitMQ/SQS) would lose
replay and multi-consumer fan-out; a database table as a queue would not scale.

### Why Spark?
For **throughput-oriented** stream processing that must land in the lake: parsing and validating
every event, quarantining bad records, writing partitioned Parquet with exactly-once file sinks,
and computing event-time windows with watermarks and checkpointed state. The same DataFrame code
scales from `local[2]` to a cluster and runs batch backfills over the lake. Spark is *not* used
for the per-transaction decision: micro-batches (seconds) and cross-entity state (device ↔
accounts, receiver in-degree) fit a dedicated service with an online store better. That is a
deliberate split, not an accident.

### Why batch + streaming?
They answer different questions. Streaming answers "should this transaction go through *now*?"
(milliseconds, per event, current state). Batch answers "what happened, how good are our models,
who is churning?" (complete data, late labels, heavy joins, reproducible history, training sets).
Fraud labels arrive days later, so evaluation, retraining, graph analytics and the warehouse are
inherently batch. The two paths share the **same feature code and policy**, which is what keeps
them consistent (a Lambda-style architecture without two implementations of the logic).

### Why XGBoost?
Tabular, heterogeneous, non-linear features with interactions (new device × high amount × night),
tens of thousands of rows, strong class imbalance, and a need for explanations. Gradient-boosted
trees are the state of the art for this regime, train in seconds, handle monotone-ish and
missing-ish values well, support `scale_pos_weight`, and provide **exact TreeSHAP** attributions
natively (`pred_contribs=True`), which the API uses for reasons. Single-row inference with
`inplace_predict` is ~1 ms. LightGBM would be equivalent; deep nets would need far more data and
give weaker, harder-to-explain results on this data.

### Why PR-AUC instead of accuracy?
With ~1% fraud, a model that approves everything is 99% accurate and useless. ROC-AUC is also
flattering under imbalance because the false-positive rate is divided by a huge number of
negatives. **PR-AUC** (average precision) focuses on the positive class: how precise are alerts
as we try to catch more fraud. We also report precision@k / recall@k (fixed analyst capacity),
confusion matrices at the policy thresholds and per-scenario recall — the metrics an operations
team actually acts on. See `reports/fraud_model_comparison.md`.

### How was class imbalance handled?
1. Choose the metric first (PR-AUC, precision@k), not accuracy.
2. Treat the weighting as a hyper-parameter: `scale_pos_weight ∈ {1, √(neg/pos), neg/pos}`,
   selected on validation PR-AUC (`imbalance_experiments` in the model metadata). Heavy
   re-weighting often *hurts* ranking and always distorts probabilities.
3. Re-calibrate probabilities (Platt scaling on validation) so that `P(fraud)=0.3` means ~30%,
   which the policy thresholds rely on.
4. Choose thresholds from precision targets on validation, not 0.5.
No SMOTE: synthetic minority points in a 61-dimensional behavioural space create impossible
transactions and leak information across the temporal split.

### How was leakage prevented?
* **Point-in-time features by construction**: the training table is produced by replaying
  history through the online `FeatureEngine`; each row sees only earlier events. A unit test
  mutates *future* transactions and asserts that past feature values do not change.
* **Temporal splits** (train → validation → test by event time) for every model; the churn model
  uses snapshots whose label windows never overlap a later split's feature window.
* **Label availability**: the model is built at the end of validation and only uses fraud labels
  *reported* before then; validation rows younger than the label-maturity window (21 days) are
  excluded from calibration/threshold selection.
* **Excluded leaky fields**: current-transaction `status`/`failure_reason`, `account_status`,
  labels in a separate table, hidden ground truth (persona, mule flag) only for evaluation.

### How does real-time inference work?
Kafka event → validation (Pydantic contract; bad → DLQ) → de-duplication (`SET NX` on the
transaction id) → Redis `MGET` of four small state documents (customer, receiving customer,
device, merchant) → 61 features → fraud XGBoost, ATO XGBoost, Isolation Forest, behavioural
baseline → `risk_score = 100·max(P(fraud), P(ATO))` → policy → decision + SHAP reasons → state
commit → idempotent write to `ops.risk_decisions`, alert to `ops.fraud_alerts` and `fg.alerts`.
Measured: ~10 ms per event on one core; the Docker replay averaged ~10–17 ms with Spark sharing
the CPUs. The API uses the same `RiskScorer` for synchronous authorisation-time scoring.

### How is feature consistency maintained?
One implementation (`features/engine.py`) used by training (offline replay) and serving (API and
stream). The model bundle stores the feature list; loading a bundle whose schema differs from the
code fails at start-up. A test asserts offline replay == online event-by-event computation for
the same events, and another that Redis-backed and in-memory state give identical features. New
Redis instances are hydrated from history with the same engine (`python -m features hydrate`).
A lesson learned while building this: re-hydrating a *live* store from a historical snapshot
silently rolls state back (the retraining DAG did exactly that in an early version, erasing the
test-period activity the stream had already folded in). Hydration is now a bootstrap-only step
(`--if-empty`); a live store is only ever advanced by events.

### How would model drift be handled?
Monitor (`python -m monitoring`, dashboard, `ops.model_monitoring`): PSI per feature vs. the
training reference stored in the bundle, PSI of the score distribution, alert rate, and realised
precision/recall per week once labels mature. Interesting real finding: counters that grow with
account tenure (`n_prior_txns`, `device_txn_count`…) drift *by construction*; they are reported
separately and would be normalised by tenure in production. Response ladder: investigate →
adjust policy thresholds (no retraining, minutes) → retrain on recent data via the Airflow DAGs →
validation gates → promote; rollback is an alias move.

### How would the system scale to millions of transactions?
* Kafka: more partitions; risk-engine workers scale horizontally up to the partition count
  (autoscale on consumer lag). State is in Redis, so workers are stateless.
* Redis: cluster mode, keys hash-partitioned; state documents are bounded (24 h window, capped
  recipient/device maps).
* Scoring: ~10 ms/event/core → ~100 events/s/core; 1,000 TPS ≈ 10–20 cores plus headroom. The
  Isolation Forest is ~half the cost and could be compiled (treelite) or made asynchronous.
* Spark: cluster mode, more shuffle partitions, S3 checkpoints; bronze is append-only Parquet.
* Warehouse: partition `fact_transactions` by date, incremental dbt models instead of full
  refresh, a columnar warehouse (the SQL is portable).
* Offline features: the replay is single-threaded (1M events measured in the README); at 10M+
  shard by customer hash and handle the cross-entity features (device, receiver) in a second pass,
  or compute them with Spark window functions and keep the online engine as the reference.
* Data generation is vectorised; the LARGE (10M) preset is supported.

### How would you handle a Kafka outage?
Producers: idempotent producer with retries and a delivery timeout; beyond that, write to a local
outbox and replay. Authorisation must not depend on Kafka: the API can score synchronously with
Redis state (degraded but functional), and a conservative fallback policy (e.g. review high
amounts from new devices) applies if Redis is also unavailable. Consumers simply stop and resume
from committed offsets; Spark from checkpoints; nothing is lost within retention (7 days). After
recovery, lag is visible in Prometheus and workers are scaled out to catch up. In production:
3+ brokers, RF=3, `min.insync.replicas=2`, rack awareness.

### How are duplicate transactions handled?
At every layer, because delivery is at-least-once:
* Producer: idempotent (`enable.idempotence`) — broker retries do not duplicate.
* Risk engine: claims each `transaction_id` once (Redis `SET NX EX`) *before* updating state, so
  velocity features are not double counted; decisions are `ON CONFLICT DO NOTHING`.
* Spark: bronze keeps raw history (duplicates included, for audit); aggregates use
  `dropDuplicatesWithinWatermark(transaction_id)`.
* Warehouse: primary keys + dbt `unique` tests; the DQ job reports duplicates in bronze.
Measured: a replay with 212 injected duplicates produced exactly one decision per unique
transaction (21,152 of 21,152), and the DQ check on the bronze zone flagged exactly the
injected duplicates (212 from the replay + 5 from the integration tests = 217).
Remaining gap (documented): a crash between the state commit and the offset commit can re-apply
an event once; closing it needs Kafka transactions or a transactional outbox.

### How do fraud labels arrive later?
From case management/chargebacks, days to weeks after the transaction (simulated: lognormal,
median ≈6 days after the case ends; 5% never reported). Consequences handled in the code:
training uses labels reported before the cutoff; recent weeks are under-labelled so validation
excludes a maturity window; dashboards show *reported* fraud with an explicit caveat; the
monitoring job computes realised precision/recall only for weeks whose labels have matured.
Unreported fraud remains in training as label noise — realistic, and a reason not to over-trust
recall numbers computed on reported labels only.

### How do false positives affect customers?
A blocked legitimate payment is a failed rent payment or a family unable to receive money; it
drives calls, churn (the churn model shows failed transactions precede churn) and regulator
complaints. Mitigations: calibrated probabilities; **REVIEW** (step-up: OTP, call-back) instead
of BLOCK in the uncertain band; BLOCK only at high precision (the threshold report shows the
false positives per operating point); human-readable reasons for analysts and customer support;
feedback loop via alert status (`CONFIRMED_FRAUD`/`FALSE_POSITIVE`) into retraining.

### How are thresholds selected?
Not at 0.5 and not inside the model. `python -m ml.fraud_detection.thresholds` tabulates, for
every candidate risk score, the validation precision/recall/alert-rate (mature labels) and
confirms it on the test period. Operating targets (e.g. ≥80% precision for REVIEW, ≥92.5% for
BLOCK) come from the business: analyst capacity, cost of a missed fraud vs. a blocked customer.
The chosen values live in `configs/policy.yaml`, versioned separately from models, and can be
changed without retraining. A cost-based alternative: minimise `C_fn·FN + C_fp·FP` using the
average fraud loss and the cost of a review.

### How does graph analytics help?
Some fraud is invisible per transaction but obvious in the network: a mule receives small,
normal-looking transfers from many unrelated victims, moves them out within minutes and shares a
handset with other accounts. Graph features (in-degree of distinct senders, pass-through share,
shared devices, community membership) expose rings and hubs. In this project the unsupervised
mule score reaches PR-AUC ≈0.70 against hidden ground truth and the flagged clusters contain
all mules at ~9× the base rate (although at the very top of the list plain in-degree ranks mules
slightly better) (`reports/graph_analysis.json`). Communities also give analysts a
unit of investigation: take down a ring, not one account. The online engine carries lightweight
point-in-time network features (receiver in-degree, accounts per device); heavier global metrics
(PageRank, communities) are batch.

### Why not use deep learning everywhere?
Because it would not be better here and would be worse on things that matter: tabular data of
modest size (GBDTs win), strict latency (1 ms trees vs. heavier nets), explainability requirements
(exact TreeSHAP vs. approximate attributions), calibration, debugging and on-call cost. Deep
learning earns its place for sequences with long-range structure (transformers over a customer's
event history), graph learning with many labels (GNNs for rings), or unstructured inputs (device
fingerprints, text in disputes). The architecture makes adding such a model a new bundle behind
the same scorer and policy — when it wins on PR-AUC at equal latency, not before.

## Other questions worth preparing
* *Why is the risk score the max of fraud and ATO?* Different failure modes; either alone
  warrants action; `max` keeps the score interpretable as a probability.
* *Why Platt instead of isotonic calibration?* Few hundred validation positives; 2 parameters
  are stable and preserve ranking.
* *Why is the unsupervised model weaker yet still deployed?* It catches patterns without labels
  (some scenarios only it flags at the same alert budget) and is used as an escalation rule, not
  a primary decision.
